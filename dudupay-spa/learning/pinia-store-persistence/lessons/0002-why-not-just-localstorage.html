Lesson 0002 · Pinia Store 與 localStorage 持久化

為什麼不乾脆全部存 localStorage 就好

上一課的結尾你問了一個很自然的問題：反正資料最後都要寫進 localStorage，那乾脆讓 localStorage 當唯一的家、每次要讀寫欄位就直接 getItem/setItem，不就省了 Pinia 這一層？這一課要拆穿一個藏在問題背後的假設：持久化（撐過重新整理）跟反應性（畫面自動更新）是兩個完全不同的需求，localStorage 只解決第一個，完全不解決第二個。

這一課結束時，你會得到什麼： 能講出「如果 v-model 直接綁 localStorage，畫面會壞在哪」，並且能用一個類比向別人解釋 Pinia 跟 localStorage 為什麼是兩層、不是二選一。

先做另一個思想實驗

假設 Step1Account.vue 的 email 欄位長這樣，直接讀寫 localStorage、完全跳過 Pinia：

<input
  :value="JSON.parse(localStorage.getItem(KEY)).step1Account.email"
  @input="e => {
    const data = JSON.parse(localStorage.getItem(KEY))
    data.step1Account.email = e.target.value
    localStorage.setItem(KEY, JSON.stringify(data))
  }"
/>

你在輸入框打字，@input 有觸發，setItem 也真的把新值寫進硬碟了。但畫面上的文字會不會跟著你打的字更新？

不會。因為這個 :value 綁定的來源——那次 JSON.parse 出來的物件——只在元件第一次渲染時執行過一次。Vue 沒有任何機制知道「你剛剛改了 localStorage，要重新跑一次這段程式碼」。

為什麼 Vue「不知道」localStorage 變了

這不是 Vue 的疏忽，是 localStorage 本身設計上就沒有「這一分頁內」的變更通知機制。MDN 官方文件寫得很白：storage 事件只會在「其他」分享同一個 origin storage 的分頁觸發，不會在做出改變的那個分頁本身觸發——瀏覽器的假設是「你自己改的，你自己當然知道」，沒必要通知自己。

Vue 的畫面更新靠的是完全不同的機制：reactive() 把物件包成一個 Proxy，每次讀取屬性它會偷偷記下「這個地方依賴這個屬性」，每次賦值它會偷偷通知「這個屬性變了，訂閱的地方請重新算」。這一整套依賴追蹤，只對活在記憶體裡、被 reactive()/ref() 包過的物件有效——字串形式躺在 localStorage 裡的資料，Vue 完全無從追蹤起。

回頭看 registration.ts 的設計：不是二選一，是兩層

  • 反應層（Pinia + reactive）：滿足「使用者現在打字，畫面現在要更新」——這是 Vue app 能動起來的最基本需求，跟要不要持久化完全無關，就算這個表單完全不需要撐過重新整理，這一層也一樣要存在。
  • 持久層（localStorage）：滿足「重新整理後資料還在」——這是額外加上去的需求，跟 Vue 怎麼渲染畫面無關。

registration.ts 做的事，是讓反應層透過 watch(..., { deep: true }) 單向廣播給持久層（改了記憶體 → 順便存一份到硬碟），而不是反過來讓 localStorage 當唯一事實來源、每次要用資料就去問它。方向很重要：記憶體永遠是「現在」最準的那份，localStorage 只是它的備份。

一個類比：工作台 vs 保險箱

Pinia state 像攤在工作台上的文件——伸手就能改，改了立刻看得到效果。localStorage 像下班前鎖進保險箱的備份——安全、扛得住停電（重新整理），但每次要用都得走去開保險箱、拿出來、鎖回去，慢很多。MDN 也指出 localStorage 的讀寫是同步、會卡住主執行緒的操作——如果讓它變成「每個按鍵都要開一次保險箱」，畫面會明顯頓。現在的設計是「工作台上隨便動，下班前（資料變動時）才鎖一次保險箱」，讀保險箱更只在開店開門（store 初始化）那一刻做一次。

那把 :value/@input 換成 v-model 呢？

不會有差別，因為兩者根本是同一件事。Vue 官方文件寫得很明確：在原生 <input> 上，v-model="x" 就是 :value="x" @input="x = $event.target.value" 的縮寫，編譯器會把它展開成一模一樣的東西。上面那段例子故意寫成長版，就是要把 v-model 這層糖衣拆開給你看——換回 v-model 語法不會多長出任何反應性，賦值的目標還是同一個 JSON.parse 出來、用完即丟的普通物件，問題原封不動。

那如果先把讀出來的資料包成 reactive() 呢？

這個提案就對了——而且這正是 registration.ts 實際在做的事。差別只在一個關鍵字：

// 壞掉的版本：普通物件，Vue 沒有追蹤能力
const data = JSON.parse(localStorage.getItem(KEY))

// registration.ts 實際的版本：包成 reactive，Vue 才追蹤得到
const step1Account = reactive({
  ...defaultStep1Account(),
  ...persisted.step1Account,   // persisted 就是從 loadPersisted() 讀出來的 JSON.parse 結果
})

兩段程式碼都「從 localStorage 讀一次資料出來」，差別在於後者多包了一層 reactive()。就是這一層，讓 Vue 能對這個物件做依賴追蹤，v-model（或 :value/@input）綁在它身上才會真的動起來——而且這時候 v-model 綁的對象其實是 Pinia state，不是 localStorage 本身，localStorage 只在 store 剛啟動那一刻被讀了一次，之後就退場，換 watch(..., persist) 單方面把最新的 state 寫回去而已。你的直覺是對的，只是少了「要包成 reactive()」這一步——而這一步做完，其實就是把 Pinia 重新發明了一遍。
