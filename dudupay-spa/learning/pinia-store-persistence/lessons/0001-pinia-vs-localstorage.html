Lesson 0001 · Pinia Store 與 localStorage 持久化

Pinia 是記憶體，localStorage 是硬碟

你對 Pinia 的認知——「可以存全域變數」——是對的，但只對了一半。這一課要補的是：Pinia 的「全域變數」到底存在哪裡、為什麼光有 Pinia 還不夠，讓 src/stores/registration.ts 裡的 localStorage.getItem / setItem 變得合理，而不是一段看起來多餘的程式碼。

這一課結束時，你會得到什麼： 能對著 registration.ts 的真實程式碼，講出「拿掉 localStorage 那幾段會壞在哪」，以及新增一個欄位時要同步改哪幾個地方。

先做一個思想實驗

如果把 registration.ts 裡所有跟 localStorage 有關的程式碼都刪掉，只留下最單純的 Pinia store：

export const useRegistrationStore = defineStore("registration", () => {
  const step1Account = reactive(defaultStep1Account())
  // ...
  return { step1Account, /* ... */ }
})

使用者填了 Step1、Step2，填到 Step3 時不小心按到瀏覽器重新整理鍵。會發生什麼事？

答案是：全部清空，回到 Step1 空白狀態。原因不是 Pinia 壞掉了，而是重新整理會把整個網頁的 JavaScript 執行環境整個丟掉、重新載入一次——Pinia store 本來就只是活在這個執行環境裡的一個 JS 物件（官方文件把 state 定義為「回傳初始值的函式」，本質上就是包成響應式的一般物件）。JS 執行環境被丟掉，這個物件當然也跟著消失。

Pinia 的「全域」，指的是「這次執行環境裡的全域」

你原本的認知——Pinia 能存全域變數——完全正確，但要補上一個限定詞：它是「這次頁面載入」範圍內的全域，不是「跨越重新整理」的全域。不管幾十個元件同時 useRegistrationStore()，拿到的都是同一個 singleton 物件，這是 Pinia 的核心價值；但這個 singleton 本身就是一坨活在瀏覽器分頁記憶體裡的 JS 資料，跟你電腦硬碟上的檔案系統是兩個完全不相干的地方。Vue 的 reactive() 只負責讓這坨資料「改了會自動觸發畫面更新」，一樣不負責讓它撐過重新整理。

要撐過重新整理，資料必須被寫進瀏覽器記憶體以外的地方——這正是 localStorage 的角色：它是瀏覽器提供的一塊硬碟等級的 key-value 儲存空間，跟這次頁面的 JS 執行環境完全獨立，重新整理、關分頁、甚至關瀏覽器再打開，裡面的資料都還在。

逐段拆解 registration.ts

把這份檔案看成一個四段的循環，每段對應一個問題：

1. loadPersisted() — 硬碟上有沒有留東西？

function loadPersisted(): Partial<PersistedShape> {
  const raw = localStorage.getItem(STORAGE_KEY);
  if (!raw) return {};
  try {
    return JSON.parse(raw) as Partial<PersistedShape>;
  } catch {
    return {};
  }
}

store 一啟動就先去 localStorage 問一次：「上次有沒有存過東西？」localStorage 只能存字串，所以存進去的是 JSON.stringify 過的字串，讀出來要 JSON.parse 解回物件——try/catch 是防資料格式壞掉（比如你手動改過 schema）時整頁噴錯。

2. reactive({ ...default, ...persisted }) — 拿硬碟資料墊出這次的記憶體資料

const step1Account = reactive<Step1Account>({
  ...defaultStep1Account(),
  ...persisted.step1Account,
});

這就是 Pinia state 真正誕生的地方。邏輯是「先用預設值墊底，如果 localStorage 裡有上次填過的資料就蓋過去」——所以使用者上次填到一半的 email、手機號碼，重新整理後看起來像是「還在」，其實是重新從 localStorage 讀出來、重新蓋出一個新的 reactive 物件，不是原本那個記憶體物件真的活下來了。

3. watch([...], persist, { deep: true }) — 記憶體資料一變，就準備寫回硬碟

watch(
  [step1Account, step2Upload, /* ...其餘欄位 */, completedSteps],
  persist,
  { deep: true },
);

這裡的 { deep: true } 不能省。Vue 官方文件說明 watch 預設只在「整個來源被換成另一個物件」時才觸發；但這裡改的是 step1Account.email = "..." 這種巢狀屬性賦值，物件本身的參考位址沒變，不加 deep: true 的話這個 watch 根本不會被觸發，欄位改了也不會存檔。

4. persist() — 真的把資料寫回硬碟

function persist() {
  const snapshot: PersistedShape = { step1Account, step2Upload, /* ... */ };
  localStorage.setItem(STORAGE_KEY, JSON.stringify(snapshot));
}

把目前 Pinia state 打包成一個純物件、序列化成字串，寫回 localStorage。下次使用者重新整理，回到步驟 1 loadPersisted()，循環重新開始。

一句話總結分工： Pinia + reactive 負責「這次頁面開著的時候，資料怎麼在元件之間共享、怎麼讓畫面跟著資料變」；localStorage 負責「資料怎麼撐過重新整理」。兩者互不知道對方存在——是 registration.ts 這份程式碼手動把它們接在一起的。Pinia 官方生態圈裡最常見的做法其實是裝一個外掛（pinia-plugin-persistedstate）自動做這件事；這個專案選擇手寫，所以你才會在 store 裡直接看到 localStorage 的呼叫。
