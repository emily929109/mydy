Lesson 0001 · 資料夾結構設計

為什麼是 type → config → store → router？

你已經看出來了：type 定義各步驟表單型別、整合成 StepKey；config 依賴 type 定義步驟順序；store 依賴 type + config 控制表單狀態；router 依賴前三者控制路由。這個觀察是對的。這一課要補的是「為什麼非得照這個方向不可」。

這一課結束時，你會得到什麼： 能對著 dudupay-spa 的真實程式碼，說出四層各自「唯一」的職責是什麼，並且能推理出「如果依賴方向反過來會壞在哪」。

先看規則本身

這個模式有個名字，叫單向依賴（unidirectional dependency）：

上層可以 import 下層，下層永遠不能 import 上層。

這不是 dudupay-spa 自己發明的規矩。Feature-Sliced Design（一套前端分層架構方法論）把它寫成明文規則：一層只能 import 「嚴格在它下面」的層。這是這一課要你帶走的主要外部參考來源，值得花五分鐘讀一下它的 Layers 頁面。

四層各自唯一的職責

1. types/registration.ts — 資料長什麼樣子

export interface Step1Account {
  password: string
  confirmPassword: string
  email: string
  ...
}

export type StepKey =
  | 'step1Account'
  | 'step2Upload'
  | ...

這一層零依賴，什麼都不 import。它只回答一個問題：「Step1 的資料長什麼樣子？」「總共有哪些步驟名字？」它是純詞彙表，沒有任何邏輯、沒有任何順序資訊、沒有任何「現在填到哪」的概念。

2. config/registrationSteps.ts — 步驟的順序長什麼樣子

// 7 步驟的順序/路徑/標題單一事實來源。RegisterWizardNav、router 都讀這份，
// 不在別處寫死步驟名稱或順序。
export const registrationSteps: RegistrationStepMeta[] = [
  { key: 'step1Account', path: '/register', title: '帳號註冊', order: 1 },
  ...
]

注意它 import 了 StepKey（來自 type），但沒有 import store 或 router。它只回答：「這些步驟該用什麼順序排、對應哪個網址、標題叫什麼？」這是這個檔案裡的原始碼註解自己講的重點：單一事實來源。之後你會看到這句話為什麼是整個分層設計的關鍵。

3. stores/registration.ts — 現在的即時狀態是什麼

function firstIncompleteStepPath(): string {
  const next = registrationSteps.find(
    (step) => !completedSteps.value.includes(step.key),
  )
  return next ? next.path : registrationSteps[0].path
}

Store 依賴 type（知道每個 step 資料長怎樣）+ config（firstIncompleteStepPath 要照 config 的順序去找「第一個沒完成的步驟」）。它回答的是：「使用者現在填到哪、填了什麼、存到 localStorage 了沒。」它不知道網址怎麼設計、不知道哪個 component 對應哪個步驟——那是 router 的事。

4. router/index.ts — 現在准不准去某個網址

router.beforeEach((to) => {
  const targetStep = registrationSteps.find((step) => step.path === to.path)
  if (!targetStep) return true

  const store = useRegistrationStore()
  const precedingSteps = registrationSteps.filter((step) => step.order < targetStep.order)
  const allPrecedingDone = precedingSteps.every((step) => store.isStepCompleted(step.key))
  ...

Router 是唯一同時依賴 type、config、store 三者的層。它把「步驟順序」（config）跟「目前完成到哪」（store）兜在一起，回答最後一個問題：「使用者現在能不能進這個網址？」這是這個功能裡跟瀏覽器網址列直接打交道的地方，也是離「使用者實際點了什麼」最近的一層——所以它站在最上面，可以看到下面所有人。

如果方向反過來，會壞在哪？

假設你想在 types/registration.ts 裡順手加一個工具函式，判斷某個 step 的網址是不是目前這頁，於是你打算 import router from '../router'。這樣做會壞在兩個地方：

  • 循環依賴：router 已經 import 了 type（透過 StepKey）。如果 type 又反過來 import router，兩個檔案互相依賴，形成一個環。少數情況下打包工具能勉強跑起來，但沒有人說得清「先初始化哪一個」，任何小改動都可能踩到意料外的執行順序。
  • 職責混在一起：type 的存在理由是「純資料形狀」，一旦它需要知道網址、需要知道路由怎麼運作，它就不再是穩定的詞彙表了——以後改路由設計，連帶要改 type，而 type 被幾乎每個檔案 import，牽一髮動全身。

這就是為什麼穩定、沒有副作用的東西（資料形狀）放最底層，會變動、有副作用的東西（瀏覽器網址、導航）放最上層：底層被很多人依賴，所以要盡量少變、盡量不知道別人的存在；上層依賴很多人，但只有它自己依賴自己，改動的影響範圍反而最小。

Single source of truth 的回報在哪裡

回頭看 config/registrationSteps.ts 那句註解：「不在別處寫死步驟名稱或順序」。因為 store 的 firstIncompleteStepPath 和 router 的路由表 + 導航守門邏輯，全部都是從 registrationSteps 這一份陣列讀出來的，你要調整步驟順序、改某步驟的網址，只需要改 config 這一個檔案，store 和 router 會自動保持同步。

如果沒有這層分工，store 和 router 很可能各自寫一份「步驟清單」，改一次順序要記得改兩個地方——忘了改其中一個，就是那種「明明測過為什麼還是壞」的 bug。
