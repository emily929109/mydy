Lesson 0001 · ASP.NET MVC 5 Bundling and Minification

Bundle 雜湊版號：為什麼它同時解決快取命中與破快取

上次諮詢已經決定方向了 — 這堂課只做一件事：把「為什麼」講到你能自己跟同事解釋清楚，並抓出唯一一個會讓整個方案失效的地雷。

先回顧一下卡住的地方

你試過兩個方案，都有明確的失敗原因：

  • 方案一： ?v= 接 Date() 時間戳 — 每次都不同，快取永遠 miss，等於沒有快取。
  • 方案二： 前端 fetch HEAD 打 IIS 拿 Last-Modified 比對 — 首頁要同步等這次 request 跑完才敢渲染，造成白屏約 3 秒。

兩者的共同病根其實是同一個：版號的決定時機不對。時間戳是「每次都重新決定」，fetch HEAD 是「瀏覽器端在 render 之後才決定」。Bundling 解決這兩個問題的方式，是把版號的決定時機挪到伺服器產生 HTML 的當下，而且只在內容真的變了才變。

雜湊版號怎麼運作

當你在 View 裡寫 @@Scripts.Render("~/bundles/common")，MVC 會把它展開成類似這樣的 HTML：

<script src="/bundles/common?v=r0sLDicvP58AIXN_mc3QdyVvVj5euZNzdsa2N1PKvb81"></script>

官方文件是這樣描述這個 v 的：

The query string v has a value token that is a unique identifier used for caching. As long as the bundle doesn't change, the ASP.NET application will request the bundle using this token. If any file in the bundle changes, the ASP.NET optimization framework will generate a new token, guaranteeing that browser requests for the bundle will get the latest bundle. — Bundling and Minification, §Bundle Caching — Microsoft Learn

關鍵在於這個 token 是依 bundle 內所有檔案的內容算出來的雜湊值，不是時間、不是 Last-Modified：

  • 內容沒變 → 雜湊一樣 → 網址一樣 → 瀏覽器直接吃本地快取，連 request 都不會發
  • 內容變了（哪怕只改一個字元）→ 雜湊不同 → 網址整個不同 → 瀏覽器一定會發新 request 抓最新版

而且這個雜湊是伺服器 render HTML 的當下就算好、直接寫進 HTML 屬性裡的。沒有額外的 runtime 判斷、沒有 fetch、沒有等待 — 這就是為什麼方案二的白屏問題在這裡完全不存在。

意外的附帶好處

Bundling 同時把多個檔案合併成一個 request，官方文件的範例數據是 request 數從 34 降到 9、載入時間減少 53%。對你提到「伺服器效能吃緊」的疑慮，這是直接的緩解，不是額外負擔。

唯一的地雷：Debug 模式會讓這一切失效

雜湊版號機制不是永遠開著的。它由兩個設定共同決定：

設定值結果
web.config 的 <compilation debug="...">true不合併、不壓縮、不產生雜湊版號
同上false合併＋壓縮＋雜湊版號，全部生效
BundleTable.EnableOptimizations（C# 程式碼）true強制生效，蓋過 web.config 的 debug 設定

官方文件原文：

Unless EnableOptimizations is true or the debug attribute in the compilation Element in the Web.config file is set to false, files will not be bundled or minified. — 同上, §Controlling Bundling and Minification

套回你的情境：測試環境用 Debug 沒關係（開發方便除錯，本來就不需要這個機制）。但如果正式環境的 Publish Profile 沒有確實切到 Release、或 web.config 忘了把 debug 改回 false，這個方案會完全不生效 — 而且不會跳出任何錯誤，你只會發現版號問題原封不動地回來了。這就是 handoff 文件裡標記為「關鍵地雷」的原因，也是下週一 checklist 的第一項要查證的事。

附帶答案：Q8 的一部分已經解決了

官方文件另外提到一件事，直接回答了 handoff 裡 Q8 的一半：

Bundles set the HTTP Expires Header one year from when the bundle is created. — 同上, §Bundle Caching

也就是說，bundle 本身的回應（那個 ?v=... 網址背後的 handler）已經自動帶了一年後過期的 Expires header，不需要你在 IIS 另外設定。IIS web.config 的 <staticContent><clientCache> 設定，只對沒有走 bundling 的靜態檔案（例如圖片、字型）有意義 — 這部分下週一還是要查證有沒有設，但 JS/CSS 的長效快取本身已經不用你操心。細節整理在速查表。
