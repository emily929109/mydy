前端拿到的 response，是後端哪一行 return 的？

目標：看到 /api/Upload/PostFormData 的回應，能指出是 Utilities.cs 的哪一個 return 產生的。順便學會讀 C# 的方法簽章、new { } 和 try/catch。

先看全貌：一個 response 裡有四個「狀態」

前端收到的東西，其實是好幾層程式一層包一層決定的。由外往內：

① HTTP 狀態碼（Network 面板看到的 200 / 401 / 500）
誰決定：ASP.NET Web API 框架
② success / msg
誰決定：Utilities.Upload_register（:349）——只代表「照片有沒有存好」
③ value.ocr.status（ok / skip / duplicate / fail / error）
誰決定：Utilities.CheckIdIdentify_register（:700）
④ value.ocr.http_status
誰決定：OCR 主機回給 IDApi.cs 的 HTTP 碼。不是我們後端的碼！

今天只處理 ① 和 ②：Upload_register 有哪幾個出口、每個出口長什麼樣。③④ 留給後面幾課。

C# 方法簽章：型別寫在名字前面

你在 TS 課學過「名字: 型別」。C# 剛好反過來，是「型別 名字」：

TypeScriptC#
msg_txt: stringstring msg_txt
fi: FileInfo[]FileInfo[] fi
function f(): Promise<ReturnMsg>Task<ReturnMsg> f()

所以這一行要這樣拆（Utilities.cs:349）：

349
public async Task<Layout.ReturnMsg> Upload_register(HttpRequestMessage Request, string msg_txt)
  • public：別的檔案（UploadController）可以呼叫它。
  • async Task<Layout.ReturnMsg>：回傳型別。Task<T> 大致等於 JS 的 Promise<T>，等它跑完會拿到一個 Layout.ReturnMsg（就是有 success、msg、value 的那個物件）。
  • Upload_register：方法名稱。
  • 括號裡：兩個參數，每個都是「型別 名字」。

Upload_register 的出口

一個方法遇到 return 就結束，return 的東西會一路傳回 controller、再變成前端的 JSON。所以「找出口」就是「找 return」。成功的出口在最下面：

三個新語法：

  • object ocr = ...：宣告變數，型別也寫在前面。object 是「什麼都能裝」的型別，像 TS 的 unknown。
  • new { status = "skip" }：匿名型別，臨時造一個物件，不用先定義 class。等於 JS 的 { status: "skip" }，只是用 = 不用 :。 new { ocr } 則是用變數名當屬性名，跟 JS 的 { ocr } 縮寫一模一樣。 （Microsoft Learn: Anonymous types — Inferred property names）
  • new Layout.ReturnMsg() { success = true, ... }：建立一個有名字的 class 的物件，然後在大括號裡順便設定屬性。

所以 :496–:509 的意思是：先假設不用辨識（skip）；如果是身分證正面 ID0A 或反面 ID0B，就把 ocr 換成辨識結果。最後一律 success = true。

那 HTTP 狀態碼呢？幾乎永遠是 200

依追蹤紀錄，UploadController.PostFormData 把 Upload_register 的回傳值直接丟回前端，回傳的是一般物件（ReturnMsg），不是 HttpResponseMessage。微軟文件寫得很清楚：

For all other return types, Web API uses a media formatter to serialize the return value. … The response status code is 200 (OK). — Action Results in Web API 2

所以 success: false、ocr.status: "fail" 統統是 200。你不會在 Network 面板看到紅字，要看 body。 只有兩種情況不是 200：

  • 例外沒被任何 catch 接住 → 框架預設回 500 （Exception Handling in Web API）。
  • 程式主動丟 HttpResponseException → 用它指定的碼。例如 MemberController.cs:47 登入資訊不完整時丟 401。上傳 API 的 JWT 檢查（[JwtAuthActionFilter_General]）不在本機，失敗時實際回什麼碼要再確認。

閉卷挑戰

不要往上捲。對每個回應，先在紙上寫下「哪一行 return 的」，再點開看答案。

A. 200，{ success: false, msg: "註冊上傳照片 失敗Out of memory." }

:513 的 catch → :517 的 return。msg 的格式就是 :520 的 msg_txt + " 失敗" + e.Message。（.NET Framework 的 Image.FromFile 讀到不是圖片的檔案會丟 OutOfMemoryException，名字很誤導。）z_ErrorLog 會有一筆 level 1 的紀錄。

B. 200，{ success: true, value: { ocr: { status: "ok", data: { papa_nameu: … } } } }

:505 的 return。img 是 ID0B（反面），所以 :501 有執行，ocr 被換成辨識結果。

C. 500，body 是框架產生的錯誤訊息，沒有 success 欄位

不是 Upload_register 的任何 return。是有例外沒被 catch 接住（例如 :351），框架自己回 500。這時 z_ErrorLog 不會有 Upload_register 寫的那筆 log。

今天的收穫
success: true 只代表照片存好了，辨識結果要看 value.ocr；HTTP 碼幾乎都是 200，要看 body。 你現在能讀「型別 名字」的方法簽章、new { }，也能從 response 找回 Upload_register 的出口。 整理好的對照表在 速查表。
